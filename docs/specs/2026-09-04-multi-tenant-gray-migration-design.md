# 标准运维多租户版本灰度迁移设计

## 文档状态

- 日期：2026-09-04
- 状态：设计已确认
- TAPD：[标准运维内部环境多租户版本平滑迁移](https://tapd.woa.com/10131351/prong/stories/view/1010131351137932246)
- 范围：标准运维内部环境由当前单租户版本迁移到多租户代码版本
- 运行模式：多租户版本上线初期仍开启单租户模式

## 1. 背景

当前环境运行的是标准运维单租户版本，线上模块包括：

- `default`
- `api-server`
- `pipeline-worker`
- `callback-server`
- `cleaner`
- `api-inner`
- `open-plugin`

内部环境的实际发布源不是开源仓库分支本身。当前发布链路会先把 GitHub `master`
同步到工蜂 `V3.6.X`，叠加内部环境专用代码，再分别生成 Web、API Server、
Pipeline Worker、Open Plugin、Cleaner 等模块制品。因此本次迁移还必须覆盖工蜂内部
代码及其发布流水线，不能直接把开源多租户分支部署到内部环境。

本次迁移同时涉及 Python、Django、Celery、bamboo-pipeline 和 bamboo-engine 的大版本升级：

| 项目 | 当前版本 | 目标版本 |
|---|---:|---:|
| Python | 3.6.12 | 3.11.10 |
| Django | 3.2.25 | 4.2.30 |
| Celery | 4.4.0 | 5.2.7 |
| bamboo-pipeline | 3.24.16 | 4.0.4 |
| bamboo-engine | 2.6.5 | 3.0.5 |

升级前后 Celery 任务签名、运行时依赖和租户上下文存在差异，不能让两代 Worker
随机消费同一消息。另一方面，线上可能存在持续时间较长、暂停中、等待中或正在
重试的任务，因此不能通过一次性停机替换完成升级。

内部环境在目标版本上线后仍可作为单租户使用，所以灰度维度不是 `tenant_id`，而是
标准运维业务标识 `bk_biz_id`。

## 2. 目标

1. 除页面功能变化外，用户无明显迁移感知。
2. 迁移期间旧任务不中断、不丢失、不重复、不跨运行时执行。
3. 以 `bk_biz_id` 为单位逐批灰度，观察稳定后再全量。
4. 旧版本承担临时兼容和路由职责，多租户目标版本保持干净。
5. 旧版现有 RabbitMQ、Redis、队列和进程配置不迁移、不改名。
6. 灰度期间共享同一个 MySQL，不引入业务数据双写和异步同步。
7. 旧任务全部排空后才允许把后台权威入口切换到新版。
8. 迁移结束后能够删除 Bridge、临时路由表和旧页面适配层。
9. 新旧两套灰度制品都从工蜂发布，目标制品包含完成 Python 3.11 改造的长期内部能力。

## 3. 非目标

- 不在迁移期间把正在运行的 bamboo-engine 2.x 任务转换为 engine 3.x 任务。
- 不让旧版本直接构造新版 Celery 消息或操作新版内部实现。
- 不为了命名对称把现有 `/bk_sops` vhost 改名为 `/bk_sops_legacy`。
- 不建立一套新旧业务数据库并进行长期双写。
- 不把临时的版本判断、旧表兜底或旧引擎状态兼容带入多租户主干。
- 不在 legacy 活跃任务未归零时下线旧 Worker 或把后台权威入口切到新版。
- 不直接把开源 `dev_multi_tenant` 分支作为内部环境发布制品。
- 不把工蜂 `V3.6.X` 整体合入多租户目标分支，也不原地升级旧运行面的 Python。

## 4. 核心原则

### 4.1 新任务按业务灰度，已有任务按任务粘滞

- 创建新任务时，旧版 Bridge 根据稳定、可审计的 `bk_biz_id` 白名单决定运行通道。
- 任务创建成功后，其运行通道在整个生命周期内保持不变。
- 查询、操作、回调、重试、撤销和补偿均根据 `task_id` 的固定路由执行。
- 业务退出灰度只影响之后创建的新任务，不能搬迁已经创建的 mt 任务。

路由优先级为：

```text
已有 task_id 的路由记录 > bk_biz_id 灰度配置 > 默认走现有旧版
```

### 4.2 临时迁移复杂度留在旧版

基于旧版本发布一个 Bridge Release。它负责灰度判断、路由、转发、迁移审计和
共存期数据兼容。迁移结束后，这些能力随旧版本一起删除。

多租户目标版本只保留：

- 单租户/多租户运行模式；
- 目标领域模型与租户上下文；
- 新版 Celery/bamboo-engine 执行链路；
- 正式公开且需要长期支持的 API 契约；
- 对第三方系统的长期适配器；
- 自身任务的幂等、回调和可观测能力。

### 4.3 旧运行资源零迁移，新运行资源只增不改

旧版继续使用现有 `/bk_sops`、队列、账号、Redis 和进程配置。新版只创建新增的
隔离资源。文档中的 `legacy` 是逻辑标签，不要求修改现有资源名称。

### 4.4 页面与后台权威入口解耦

旧页面可以比旧后台保留更长时间。后台切换到新版后，旧页面被视为新版后台的一个
客户端，通过隔离的接口适配层访问新版领域服务，不再写入旧后台。

### 4.5 新旧制品都经过工蜂集成，旧运行面不升级

- 旧版 Bridge 以工蜂 `V3.6.X` 为基线，继续使用 Python 3.6、Django 3.2、Celery 4
  和现有发布流水线，只增加迁移期 Bridge 能力。
- 目标版本以开源 `dev_multi_tenant` 为代码基线，在工蜂建立独立的多租户集成主线，
  逐项移植需要长期保留的内部代码，并完成 Python 3.11、Django 4.2、Celery 5 适配。
- 工蜂旧分支中的历史依赖、旧引擎兼容和迁移期路由不得整体带入目标版本。
- 工蜂内部代码的差异清单、移植状态和验证证据是业务进入灰度前的硬门禁。

## 5. 总体架构

```text
 GitHub master -----------------> 工蜂 V3.6.X + Bridge 改造
                                      |
                                      v
                               工蜂旧版模块制品
                               Python 3.6 / Celery 4

 GitHub master -> release_humming_bird -> dev_multi_tenant
                                      |
                                      v
                         工蜂多租户集成主线 + 内部代码移植
                                      |
                                      v
                               工蜂目标模块制品
                               Python 3.11 / Celery 5

                         页面 / OpenAPI / 第三方回调
                                      |
                                      v
                    +----------------------------------+
                    | 工蜂旧版 Bridge Release          |
                    | - bk_biz_id 灰度                 |
                    | - task_id 固定路由               |
                    | - 协议转换与回调分发             |
                    | - 熔断、审计与幂等协调           |
                    +----------------+-----------------+
                                     |
                          HTTP internal API
                       /             |              \
                      v              v               v
          工蜂旧版原有链路       临时路由表       工蜂多租户目标版本
          现有 /bk_sops          共享 MySQL       新增 /bk_sops_mt
          现有 Redis                              新版独立 Redis
          旧 Worker                               新 Worker
```

Bridge 是灰度期唯一后台公共入口，但不要求亲自渲染所有页面。它可以将灰度业务的
页面资源和 API 请求代理到新版。非灰度业务继续执行原有代码路径。

不新增独立 `migration-router` 服务，路由能力进入旧版 `default`、`api-server` 和
`callback-server` 等现有入口模块。

## 6. 组件职责

### 6.1 旧版 Bridge Release

`default` / `api-server`：

- 识别 `bk_biz_id` 和 `task_id`；
- 查询灰度配置与临时路由表；
- 非灰度请求执行原有路径；
- 灰度请求调用新版版本化内部 HTTP API；
- 透传用户身份、租户默认值、业务标识和链路追踪标识；
- 执行超时、重试、熔断和审计。

`callback-server`：

- 从 `task_id` 或回调路由令牌确定运行通道；
- 旧任务执行原有回调逻辑；
- 新任务通过 HTTP 转发到新版 callback 服务；
- 记录失败并支持幂等重放。

`beat`：

- 灰度期间保持唯一全局周期调度者；
- 根据周期任务所属 `bk_biz_id` 决定在旧版建单或调用新版幂等建单 API；
- 切换前记录执行水位，防止漏调度或重复调度。

`pipeline-worker`：

- 继续使用现有 `/bk_sops`；
- 只执行现有和新建的旧版任务；
- 不消费新版 vhost，不理解新版任务签名。

`cleaner` 及其他全库扫描任务：

- 旧进程配置保持不变；
- 临时逻辑通过路由表排除新版任务；
- 需要处理新版数据时，将明确的任务 ID 通过新版维护 API 交给新版处理。

### 6.2 多租户目标版本

- 实际发布源为工蜂多租户集成主线，而不是直接发布开源分支；
- 只移植需要长期保留的内部环境能力，并完成 Python 3.11 兼容改造；
- 灰度期通过内部地址提供版本化 HTTP API；
- 使用 Python 3.11、Django 4.2、Celery 5 和 bamboo-engine 3；
- 在内部环境开启单租户模式，并使用 `DEFAULT_TENANT_ID`；
- 自己创建任务数据、发布 mt 消息并完成任务生命周期；
- 不访问 `/bk_sops`，不兼容旧 Celery 消息；
- 不包含旧任务状态机、旧表结构分支或旧运行时路由逻辑。

### 6.3 共享 MySQL

- 保存扩展后的目标业务数据；
- 同时支持旧 Bridge 和新版代码读写；
- 保存 Bridge 独占使用的临时路由表；
- 不承担跨版本消息队列或业务数据同步职责。

### 6.4 工蜂集成与模块发布

灰度期维护两条相互独立的工蜂集成线：

| 集成线 | 代码基线 | 运行时 | 允许包含的内部改动 | 发布用途 |
|---|---|---|---|---|
| 旧版 Bridge | 工蜂 `V3.6.X` | Python 3.6 / Django 3.2 / Celery 4 | 原有内部代码、临时 Bridge 能力 | 承载 legacy 任务和统一入口 |
| 多租户目标 | 开源 `dev_multi_tenant` 的锁定 SHA | Python 3.11 / Django 4.2 / Celery 5 | 已完成升级的长期内部代码、正式对接适配 | 承载 mt 任务 |

两条集成线分别生成与当前内部环境模块拓扑对应的制品。目标制品至少要覆盖页面、API、
Pipeline Worker、Callback、Cleaner、内部 API 和 Open Plugin；不能只验证 Web 模块后就
进入任务灰度。

工蜂内部差异需要按以下类别建立清单：

1. 部署、环境变量和模块启动配置；
2. 内部认证、网关、SDK 和第三方系统适配；
3. 内部插件及其依赖；
4. 页面和内部产品能力；
5. 已被开源实现替代、可以删除的历史补丁；
6. 仅 legacy 运行面需要、不得移植的旧版代码；
7. 仅迁移期需要、只能放在 Bridge 的路由与兼容代码。

清单中的每一项都必须记录来源提交、目标处理方式、负责人、Python 3.11 状态、测试证据
和适用模块。禁止通过一次整体 merge 把 `V3.6.X` 的全部历史差异带入目标集成线。

## 7. 临时路由模型

建议新增 `migration_task_route` 表，至少包含：

| 字段 | 含义 |
|---|---|
| `migration_request_id` | Bridge 为一次逻辑建单生成的唯一标识 |
| `client_request_id` | 调用方提供的可选幂等标识 |
| `bk_biz_id` | 灰度判定使用的业务 ID |
| `runtime_lane` | `legacy` 或 `mt` |
| `task_id` | 任务创建后回填，创建前允许为空 |
| `callback_route_token_hash` | 回调不携带 task_id 时使用的不可猜测令牌摘要 |
| `route_state` | `pending/creating/ready/failed/unknown` |
| `error_code/error_message` | 最近一次交接异常摘要 |
| `created_at/updated_at` | 创建和更新时间 |

约束：

- `migration_request_id` 唯一；
- `task_id` 非空时唯一；
- `client_request_id` 若存在，应与调用方和业务维度组成唯一约束；
- 迁移前没有路由记录的任务默认视为 `legacy`；
- `pending/creating/unknown` 不能按 `legacy` 兜底执行；
- 路由表只服务迁移，目标版本正式任务模型不增加 `execution_cohort` 字段。

如果外部回调不携带 `task_id`，Bridge 需要生成不可猜测的
`callback_route_token`，并将其映射到同一条路由记录。

## 8. 内部 HTTP API

### 8.1 边界

旧 Bridge 与新版只能通过版本化内部 HTTP API 交互，禁止：

- Bridge 直接向 `/bk_sops_mt` 发布 Celery 消息；
- Bridge 导入或复用新版 Python 包；
- Bridge 根据新版内部表结构拼装业务数据；
- 新版读取 Bridge 的临时路由表来决定自己的业务行为。

### 8.2 基本能力

内部 API 至少提供：

- 幂等创建但暂不启动任务；
- 根据 `idempotency_key` 查询创建结果；
- 幂等启动任务；
- 查询任务和节点状态；
- 执行暂停、继续、撤销、重试等操作；
- 接收回调；
- 接收明确任务 ID 范围的清理或维护请求。

每个接口需要：

- 独立服务鉴权；
- 明确的版本号；
- `idempotency_key`；
- `request_id/trace_id` 透传；
- 明确的超时、可重试错误和不可重试错误；
- 限流、熔断和健康检查。

### 8.3 `migration_request_id` 来源

`migration_request_id` 由旧 Bridge 为一次向新版交接的逻辑建单生成，不直接使用
APIGW 的 `request_id` 或 tracing ID。后两者通常在网络重试时变化，不能作为逻辑
建单幂等键。

Bridge 生成的标识只能消除 Bridge 到新版之间的重复。如果需要识别用户重复点击或
外部调用方重新请求，页面或调用方还需提供稳定的 `client_request_id`。

## 9. 请求与任务数据流

### 9.1 新版任务创建

为了避免新版任务已经开始执行、Bridge 尚未持久化路由，创建和启动必须分开：

```text
Bridge 生成 migration_request_id
  -> 写 pending 路由记录
  -> 将状态改为 creating
  -> 调用新版 create API，要求暂不启动
  -> 新版按 idempotency_key 幂等创建并返回 task_id
  -> Bridge 回填 task_id，状态改为 ready
  -> Bridge 调用新版幂等 start API
  -> 新版向 /bk_sops_mt 发布消息
  -> Bridge 返回建单结果
```

如果 create 或 start 超时，Bridge 必须先按幂等键查询真实状态。没有确认失败前，
不得改投旧版或生成新的幂等键。

### 9.2 旧版任务创建

非灰度业务继续执行旧版原有建单逻辑。灰度期间新建的旧版任务可以记录显式
`legacy` 路由，以便审计；迁移前的历史任务没有路由记录，按默认 legacy 处理。

### 9.3 查询、操作与回调

```text
携带 task_id 的请求
  -> Bridge 查询 migration_task_route
  -> mt：调用新版内部 API
  -> legacy：执行旧版原有逻辑
  -> 无记录：作为迁移前 legacy 任务
```

路由状态为 `pending/creating/unknown` 时返回可重试状态并告警，不能静默执行旧逻辑。

### 9.4 周期任务

```text
旧 Beat 触发周期计划
  -> Bridge 提取 bk_biz_id
  -> 非灰度：旧版原有建单
  -> 灰度：使用稳定幂等键调用新版建单 API
```

灰度期间新版全局 Beat 默认关闭。确实属于新版运行时内部、不会与旧调度重复的任务，
经过逐项审核后才允许启用。

## 10. 数据库兼容与回填

### 10.1 Expand

1. 根据线上已执行的 migration 状态新增前向迁移，不修改已执行的历史 migration。
2. 新增 `tenant_id` 时先允许为空，并在共存期保留数据库级默认值兜底。
3. 只增加字段、索引和临时表，不删除、不重命名旧字段。
4. 唯一约束需要增加租户维度时，先创建新索引并验证，再处理旧索引。
5. 大表 DDL 需要评估锁表时间并采用线上允许的变更方式。

### 10.2 Bridge 写入兼容

Bridge 在所有受多租户改造影响的写入入口显式写入 `DEFAULT_TENANT_ID`。数据库默认值
只作为漏网写入的保护，不作为正常业务逻辑。

范围至少覆盖业务、项目、流程模板、任务、周期计划、插件来源和其他新增租户字段的
模型，最终以代码和 migration 清单为准。

### 10.3 Backfill

- 按主键范围或稳定游标分批执行；
- 每批独立提交；
- 支持暂停、续跑和重复执行；
- 记录扫描、更新、跳过和失败数量；
- 控制批次大小、数据库负载和锁等待；
- 禁止用一个大事务执行全表 `update()`。

内部单租户环境统一回填为配置中的 `DEFAULT_TENANT_ID`。

### 10.4 Verify

新版开始承接真实业务前必须满足：

- 目标表 `tenant_id IS NULL` 数量为零；
- 新租户唯一索引无冲突；
- 关联记录不存在租户不一致；
- 旧版与新版读取同一业务、项目和模板的结果一致；
- Bridge 新写入数据全部带默认租户；
- 临时路由表不存在超时的 `pending/creating/unknown` 记录。

### 10.5 Contract

只有在旧任务排空、后台入口切换、新版稳定、旧页面观察期结束且 Bridge 下线后，
才允许删除临时表、旧索引和过渡默认值，并收紧最终非空约束。

## 11. 运行资源隔离

### 11.1 旧版资源保持原样

```text
RabbitMQ vhost: 现有 /bk_sops
RabbitMQ 账号: 现有账号
queue/exchange/routing key: 原名称
Redis: 原 DB、Key、锁和节点超时池
进程: 原 Worker、Beat、Cleaner 和 Exporter 启动方式
```

明确不做：

- 不把 `/bk_sops` 改名为 `/bk_sops_legacy`；
- 不迁移积压消息；
- 不重新绑定旧队列；
- 不更换旧 RabbitMQ/Redis 凭证；
- 不为了迁移修改旧 Worker 的消费队列清单。

### 11.2 新版新增资源

```text
RabbitMQ vhost: /bk_sops_mt
RabbitMQ 账号: 新版专用账号
Redis: 独立 DB 或独立实例
进程: 新版 Web/API、Worker、Callback、超时扫描和 Exporter
```

新版账号无权访问旧 vhost，旧版账号无权访问新版 vhost。即使队列名称相同，也不能
跨版本消费。

### 11.3 后台进程分类

| 类型 | 灰度策略 |
|---|---|
| 消息驱动 Worker | 新旧各自运行，只访问各自 vhost |
| Redis 扫描进程 | 新旧可并行，但必须使用独立 Redis 空间 |
| 全库扫描与全局调度 | 保持单一负责人，通过内部 HTTP API 委派新版 |
| 监控 Exporter | 新旧各一套，分别监控各自 vhost |

`node_timeout_process` 一类进程会扫描 Redis 节点池，再写数据库和投递处理任务。新版
必须使用独立的执行节点池、锁和队列，避免旧扫描进程捞到新版节点。

## 12. 页面与后台切换阶段

### 阶段 A：按业务灰度

- 旧 Bridge 是后台统一入口；
- 旧页面服务非灰度业务；
- 新页面可服务灰度业务；
- 两套页面的 API 请求均先经过 Bridge；
- 旧、新任务分别进入各自运行时。

### 阶段 B：全量新版建单

- 所有业务的新任务都由 Bridge 转发新版；
- 旧页面仍可使用；
- legacy 任务继续由旧 Worker 执行；
- Bridge 继续按 task_id 路由旧任务操作。

### 阶段 C：后台权威入口切新版

必须先满足 legacy 排空硬门禁。切换后：

- 新版成为唯一后台权威写入端；
- 新页面调用新版正式 API；
- 旧页面调用新版隔离的 `legacy-ui API adapter`；
- 两种 API 最终调用同一套新版领域服务；
- 旧 Bridge 和旧 Worker 不再写入业务数据。

`legacy-ui API adapter` 只能转换参数、响应和长期外部契约，不能引入旧模型、旧队列或
旧引擎状态机。

### 阶段 D：旧页面下线

观察期结束后停止旧页面入口，并删除对应的 `legacy-ui API adapter`。新版页面、正式
API、新版运行时进入长期维护状态。

## 13. 灰度计划

### 13.1 灰度批次

使用显式业务白名单，不做逐请求随机比例：

```text
内部测试业务
  -> 低风险业务
  -> 插件和任务类型覆盖较完整的典型业务
  -> 大任务量或长周期业务
  -> 所有业务
```

每批至少覆盖一个完整业务使用周期和周期任务触发周期。

### 13.2 每批放量门禁

- 该业务使用的流程模板、内部插件、API、周期任务和回调能力均在目标工蜂版本中标记为可用；
- 目标工蜂版本的所有相关模块已完成 Python 3.11 构建、部署和冒烟验证；
- 重复建单为零；
- 路由错误和跨版本执行为零；
- 超时 `pending/creating/unknown` 路由记录为零；
- 新版任务成功率、启动延迟和完成耗时不劣于旧版基线；
- 卡住任务、异常终止和回调失败没有明显上升；
- `/bk_sops_mt` 队列没有持续积压；
- 新版 Redis 超时池、锁和任务状态一致；
- 旧页面和新页面操作同一新版任务的结果一致；
- 没有需要人工修复的数据不一致。

## 14. Legacy 排空门禁

不能只检查 Celery 队列为空。后台权威入口切换前必须同时确认：

- 旧版运行中、暂停中和等待中的任务为零；
- 旧引擎活跃 Process/State 记录为零；
- ETA、retry 和 schedule 消息为零；
- 未完成回调、补偿和异步操作记录为零；
- Redis 执行节点池和相关锁为零；
- 周期任务不会再创建旧任务；
- 临时路由表中没有活动的 legacy 任务；
- 旧 Cleaner 和全局扫描任务不存在待处理旧数据。

这个门禁是后台入口切换和停止旧 Worker 的必要条件。

## 15. 异常处理与回滚

### 15.1 建单状态机

```text
pending -> creating -> ready
                  \-> failed
                  \-> unknown
```

- `pending/creating` 不能向用户返回成功；
- `unknown` 必须按幂等键查询新版真实结果；
- 只有确认新版未创建任务后，才允许用户重新提交；
- 任何异常都不能自动改投旧版；
- 新版任务只有在路由记录 `ready` 后才能启动。

### 15.2 灰度回退

- 关闭业务灰度只影响之后的新任务；
- 已创建的 mt 任务继续由新版执行；
- 新版异常时停止放量，但不能下线仍有活动任务的新版 Worker；
- Schema Expand 不执行逆向 DDL 回滚；
- Bridge 调用超时时先查询真实结果，禁止重新生成幂等键建单；
- 后台入口切到新版后可以恢复旧页面，但不能恢复旧后台权威写入。

## 16. 可观测性

日志、指标和追踪至少包含：

```text
bk_biz_id
runtime_lane
task_id
migration_request_id
client_request_id（若有）
app_module
release_version
request_id / trace_id
```

核心监控：

- 按业务和通道统计的新建任务量；
- 路由状态数量与停留时间；
- 重复任务、路由缺失和跨版本消费；
- 新旧任务成功率、耗时和卡住率；
- Bridge 到新版 HTTP 的延迟、错误和熔断状态；
- 两个 vhost 的队列长度、最老消息年龄和消费者数量；
- Worker 心跳、Redis 超时池与锁；
- 回调失败、重试和补偿；
- 数据迁移耗时、锁等待和回填进度。

## 17. 测试与演练

### 17.1 功能与契约

- 对工蜂内部能力清单逐项执行 Python 3.11 导入、初始化和功能测试；
- 扫描待灰度业务的流程模板，确认引用的每个内部插件都存在于目标制品并通过验证；
- 旧页面、 新页面、OpenAPI 和周期计划分别创建新版任务；
- 查询、暂停、继续、撤销、重试和节点操作；
- 子流程、长任务、超时节点和失败补偿；
- 第三方插件与回调；
- 后台入口切换后旧页面继续操作新版数据；
- 新版接口适配层最终进入同一套新版领域服务。

### 17.2 故障注入

- Bridge 调用新版前后分别被中断；
- 新版已创建任务但 Bridge 未收到响应；
- Bridge 写路由成功但启动请求超时；
- 新版 API、RabbitMQ 或 Redis 短暂不可用；
- 业务退出灰度后继续操作已存在的 mt 任务；
- 回调重复、乱序和延迟到达。

### 17.3 数据与基础设施

- 验证 Bridge 和 Target 均由工蜂流水线生成，且制品记录各自的源分支与精确 SHA；
- 验证目标 Web、API、Pipeline Worker、Callback、Cleaner、内部 API 和 Open Plugin
  使用同一组已验收的多租户集成版本；
- 使用接近线上规模的数据副本演练 Expand 和分批回填；
- 验证新增索引和约束的锁影响；
- 分别向两个 vhost 投递测试消息，确认无法跨版本消费；
- 验证旧版 MQ、Redis、队列和启动配置未变化；
- 演练旧 Beat 到新 Beat 的执行水位交接；
- 完整演练 legacy 排空和后台入口切换。

## 18. 最终验收标准

- 用户域名、鉴权和主要操作方式稳定；
- 页面变化之外无明显使用感知；
- 任务不丢失、不重复、不跨运行时；
- 新版不包含旧引擎、旧队列和旧表结构兼容；
- 旧运行资源未迁移、改名或重新绑定；
- 新旧版本共享兼容 Schema，但不存在业务数据双写；
- legacy 活跃任务归零后才切换后台权威入口；
- 后台切换后旧页面只访问新版后台；
- Bridge、临时路由表和旧页面适配层均有明确删除阶段。
- 旧版制品继续来自工蜂 `V3.6.X`，且未发生 Python、MQ、Redis 或 Worker 原地升级。
- 新版制品来自工蜂多租户集成主线，内部代码的 Python 3.11 迁移清单全部关闭。
- 每个灰度业务引用的内部插件和对接能力均通过目标版本准入检查。
