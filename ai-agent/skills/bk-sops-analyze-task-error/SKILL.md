## 概述

本 Skill 对标准运维单次任务的执行失败结果进行标准化分析。用户提供 `bk_biz_id` 与 `task_id` 后，通过失败原因分析工具拉取任务上下文数据，Skill 据此输出：失败概要、节点级原因分析（含 JOB 节点日志与脚本片段、子流程节点缩进展示）以及可操作的解决步骤。

| 能力 | 说明 |
|------|------|
| **失败概要** | 展示所属业务、任务名称、业务 ID、任务 ID 与失败节点清单 |
| **节点分类展示** | 区分普通节点、带脚本 JOB 节点、无脚本 JOB 节点、子流程节点，使用不同卡片模板 |
| **根因分析** | 分析参数依赖问题、JOB 脚本问题、其他执行问题的根本原因 |
| **解决步骤** | 按序号输出可操作的排查与修复动作 |

**解决痛点**：
- 报错信息散落在多个字段中，用户难以快速定位
- JOB 节点脚本日志与主节点日志分离，需要交叉解读
- 子流程节点错误信息层级深，容易被忽略

## 工作流程

### Step 1：问题收集

根据用户输入类型，采用不同方式收集问题信息：

| 输入类型 | 处理方式 |
|----------|----------|
| **用户提供 `bk_biz_id` + `task_id`** | 直接调用失败原因分析工具获取任务上下文 |
| **仅提供 `task_id`，未提供业务** | 引导用户补充 `bk_biz_id`；若可从对话上下文推断，需向用户确认 |
| **未提供任何 ID** | 引导用户提供，或询问是否需要通过任务列表工具查找最近失败任务 |
| **从 handoff 转入** | 接收上下文包（含 `bk_biz_id`、`task_id` 及可能的失败节点提示），直接使用已有数据 |

**输出**：确认要分析的任务标识（业务 ID + 任务 ID）。

---

### Step 2：节点类型识别

通过每个失败节点的 `component_code` 判断节点类型，决定后续展示模板：

| 节点类别 | `component_code` 取值 | 展示要求 |
|---------|----------------------|---------|
| **JOB 节点（带脚本内容）** | `job_cc_execute_script`、`job_fast_execute_script`、`all_biz_job_fast_execute_script` | 展示 **JOB 执行日志片段 + 脚本内容片段** |
| **JOB 节点（无脚本内容）** | `job_local_content_upload`、`job_execute_task`、`all_biz_execute_job_plan`、`job_fast_push_file`、`job_push_local_files`、`all_biz_job_fast_push_file` | 展示 **JOB 执行日志片段**，不展示脚本内容 |
| **普通节点** | 其他 | 仅展示节点执行日志与错误信息 |
| **子流程节点** | 判定依据为「返回数据中存在子流程错误信息」 | 用 `└─` 缩进展示内部失败子节点；子节点若为 JOB 节点则按 JOB 模板展开 |

---

### Step 3：错误类型判定与根因分析

对每个失败节点，先判定错误类型，再选择对应的分析路径：

#### 3.1 参数相关错误

**典型现象**：参数为空、缺失、格式错误、目标对象为空、变量校验失败。

##### 什么是参数依赖

节点的参数值可能不是固定的，而是引用其他地方的值（如上游节点输出、全局变量、流程输入）。**当被引用的值为空或不存在时，节点就会因为缺少必要参数而失败。** 因此分析参数错误时，必须结合依赖信息追溯参数的来源。

##### 依赖信息格式说明

依赖信息描述了「哪个参数」依赖「什么来源」，共 3 大类 6 种格式：

**类型 ①：依赖上游节点输出**
- `参数X依赖上游节点【Y】的输出` → 参数 X 的值来自上游节点 Y 执行后的输出
- `参数X依赖上游节点【Y】输出的【Z】(来源变量: V)` → 参数 X 的值来自变量 V 中的 Z 字段，该变量由节点 Y 输出

**类型 ②：来自流程输入（全局变量或节点自身输入）**
- `参数X来自流程输入` → 参数 X 的值来自全局变量或节点自身输入，不依赖上游节点
- `参数X可能来自全局变量或者节点自身输入的【V】的【Z】` → 参数 X 的值来自流程输入变量 V 的 Z 字段
- `参数X来自流程输入变量【V】中的【Z】字段` → 同上

**类型 ③：来源未知**
- `参数X引用了变量V的【Z】(来源未知)` → 无法确定该变量的具体来源，需追溯变量 V 的定义

##### 分析思路（4 步）

1. **识别「缺少什么」**：从错误信息中提取失败信号（如「目标主机为空」「参数缺失」「未选择 XX」）；
2. **定位「值应从哪来」**：从依赖信息中找到对应参数的来源：
   - 若为「依赖上游节点输出」 → 检查上游节点是否**执行成功**、是否**正确输出了该字段**；
   - 若为「来自流程输入」 → 检查用户是否**正确填写**了该参数、**全局变量配置**是否正确；
   - 若为「来源未知」 → 提示用户回流程定义中追溯变量。
3. **推断「为什么没拿到」**：结合上下文判断上游是否失败、输出字段名是否拼写错误、全局变量是否未配置；
4. **给出「应检查哪里」**：具体到某个节点名、变量名、配置项，便于用户直接定位。

##### 常见根因（5 类）

- 上游节点**执行失败**，没有产生输出；
- 上游节点执行成功，但**没有配置输出该字段**；
- **变量引用配置错误**（如字段名拼写错误、引用了不存在的变量）；
- **流程输入参数未填写**或填写错误；
- **全局变量配置缺失**或值为空。

##### 依赖信息排查方向速查表

| 描述模式 | 含义 | 排查方向 |
|---------|------|---------|
| `参数X依赖上游节点【Y】的输出` | 值来自上游节点 Y 执行后的输出 | 检查上游节点 Y 是否执行成功、是否正确输出该字段 |
| `参数X依赖上游节点【Y】输出的【Z】(来源变量: V)` | 值来自变量 V 中的 Z 字段，由节点 Y 输出 | 检查节点 Y 是否输出变量 V、V 中是否包含 Z 字段 |
| `参数X来自流程输入` | 值来自全局变量或节点自身输入 | 检查用户是否正确填写、全局变量配置是否正确 |
| `参数X可能来自全局变量或者节点自身输入的【V】的【Z】` | 值来自流程输入变量 V 的 Z 字段 | 检查全局变量 V 的 Z 字段配置 |
| `参数X来自流程输入变量【V】中的【Z】字段` | 同上 | 检查全局变量 V 的 Z 字段配置 |
| `参数X引用了变量V的【Z】(来源未知)` | 无法确定该变量的具体来源 | 检查变量 V 的定义，追溯其来源 |

> **错误分析必备要素**（写入卡片「错误分析」字段时**必须完整体现**）：
> 1. 指出**哪个参数**出了问题；
> 2. 说明该参数的值**应该从哪里获取**（根据依赖信息）；
> 3. 分析**可能的原因**（如：上游节点未输出、配置错误、执行失败等）；
> 4. 给出**排查方向**（明确用户应该去检查哪个节点/变量/配置项）。

#### 3.2 JOB 脚本执行失败

**典型现象**：错误信息中包含「任务执行失败，前往作业平台查看详情」；节点为 JOB 类节点（`component_code` 属于 Step 2 列举的9 种之一）。

##### JOB 节点特有字段

| 字段 | 含义 | 存在条件 |
|------|------|---------|
| `job_executed_log` | JOB 平台返回的脚本执行日志，包含脚本在目标主机上的实际输出（stdout/stderr） | 所有 JOB 节点 |
| `job_content` | 脚本内容，即在目标主机上执行的脚本代码 | 仅带脚本内容的 3 种 JOB 节点（快速执行脚本类） |

##### JOB 节点输出要求

- **JOB 执行日志**：只输出与错误直接相关的关键片段，**优先提取日志尾部的报错行和异常信息**，最多 100 字符；若日志**本身不超 100 字符**，可完整输出。
- **脚本内容**：只输出**导致错误的相关代码片段**，最多 100 字符；若脚本本身不超 100 字符，可完整输出。
- **截断时**在末尾注明「（完整内容请前往 JOB 平台查看）」，引导用户自行查看原始日志。
- **重点在分析，而非堆砌日志**：日志与脚本只是证据，真正有价值的是「错误分析」字段中的结论。
- **代码块包裹**：JOB 执行日志使用 ```` ```text ````；脚本内容根据语言标注（```` ```bash ````/```` ```python ````/```` ```powershell ```` 等）。

##### 分析思路（4 步）

1. **先看错误信息**，了解整体错误概况（包含作业平台链接等信息）；
2. **看 JOB 执行日志**：从尾部提取报错行和异常输出，定位具体错误位置（输出时仅展示关键片段）；
3. **看脚本内容**（仅带脚本内容的 JOB 节点）：分析脚本逻辑，判断报错原因（输出时仅展示导致错误的代码片段）；
4. **三分类给结论**：

| 问题类型 | 特征 | 典型场景 |
|---------|------|---------|
| **脚本代码问题** | 日志报错指向脚本某一行；脚本存在明显缺陷 | 语法错误（bash/python）、命令拼写错误、空值未处理、除零、下标越界 |
| **环境问题** | 日志出现 `command not found` / `permission denied` / `No such file` 等 | 目标主机缺依赖、路径不存在、权限不足（OS/文件）、磁盘满 |
| **参数问题** | 脚本中引用的变量为空或格式异常 | 变量未正确传入、上游节点未输出、全局变量为空 |

5. 引导用户前往 JOB 平台查看完整日志与脚本。

##### 常见 JOB 节点错误（6 类）

- **脚本语法错误**（bash 语法错误、python 语法错误）；
- **命令不存在或路径错误**（`command not found`、使用相对路径但工作目录不对）；
- **权限不足**（操作系统权限、文件权限、端口占用）；
- **脚本执行超时**（JOB 平台默认超时、循环阻塞）；
- **目标主机连接失败**（agent 异常、网络不通）；
- **脚本返回非零退出码**（业务逻辑主动 `exit 1`、下游命令失败）。

> **错误分析必备要素**（写入 JOB 节点卡片「错误分析」字段时**必须完整体现**）：
> 1. 指出**具体报错位置**（日志中的哪一行、脚本中的哪一段）；
> 2. 给出**问题类型判定**（脚本代码 / 环境 / 参数，三选一或组合）；
> 3. 说明**根本原因**（如「dept 字段为 None 却调用了 `.upper()`」）；
> 4. 附**修复方向**（在解决步骤中展开）。

#### 3.3 其他执行错误

**典型现象**：权限不足、网络超时、连接失败、磁盘空间不足、平台级错误。

**分析步骤**：直接分析错误信息，无需查看依赖信息；给出对应的排查方向。

> **权限相关错误**：若判定为权限类问题，按 handoff-protocol 转交 `bk-sops-permission-manager`。

### Step 4：输出规范

#### 4.1 字符限制

| 内容 | 上限 |
|------|------|
| **整体输出** | 1300 字符以内 |
| **JOB 执行日志片段** | 100 字符，优先取尾部报错行与异常堆栈 |
| **脚本内容片段** | 100 字符，只取导致错误的相关代码 |
| **错误信息** | **完整输出，不截断** |
| 日志/脚本截断处 | 追加「（完整内容请前往JOB平台查看）」 |

#### 4.2 HTML 链接转 Markdown

错误信息中如包含 `<a href='URL' target='_blank'>文字</a>`，**必须**转换为 `[文字](URL)`。示例：

```
<a href='http://job.example.com/api_execute/123' target='_blank'>前往作业平台(JOB)查看详情</a>
→ [前往作业平台(JOB)查看详情](http://job.example.com/api_execute/123)
```

#### 4.3 输出禁止事项

- **禁止在正文使用原始 JSON 字段名**（如 `dependency_info`、`failed_node_list`、`error_message`、`job_executed_log`、`job_content`、`subprocess_*`），必须用自然语言描述；
- **禁止叙述内部推理过程**（如「让我查一下依赖信息」「先解析一下 JSON」），直接输出结果；
- **禁止跨任务/跨业务信息泄露**，仅输出当前任务的分析结论；
- **敏感值脱敏**：日志、脚本、参数中出现的密码、AK/SK、Token、私钥等，输出时脱敏为 `pass****`。

#### 4.4 错误分析段落写作规范

「错误分析」是每张卡片的**核心结论字段**，必须遵循以下写作要求，**不能只复述错误信息**：

| 场景 | 段落必备要素 |
|------|-------------|
| **参数相关错误** | ① 指出出问题的**参数名** → ② 说明该参数**应从哪里获取**（依据依赖信息） → ③ 推断**为什么没拿到值** → ④ 给出**排查方向**（具体到节点 / 变量 / 配置项） |
| **JOB 脚本执行失败** | ① 指出**具体报错位置**（日志行 / 脚本行） → ② 判定**问题类型**（脚本代码 / 环境 / 参数） → ③ 说明**根本原因** → ④ 附**修复方向**（在解决步骤展开） |
| **其他执行错误** | ① 判定**错误类别**（权限 / 网络 / 超时 / 资源等） → ② 说明**触发条件** → ③ 给出**排查方向** |

**通用要求**：
- **不复述**错误信息原文，重心在**分析结论**；
- **不使用**原始 JSON 字段名，用自然语言（如「通知对象参数」而非「`notify_receivers`」）；
- **不虚构**返回数据中不存在的信息（如不能编造具体主机名、错误码）；
- **不堆砌**原始日志，只引用已在「JOB 执行日志（关键片段）」中出现的行；
- **单节点错误分析建议 60–200 字**，整体报告控制在 1300 字符以内。

## 关键 API

| API | 用途 | MCP Server |
