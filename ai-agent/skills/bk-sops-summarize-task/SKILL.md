# 标准运维任务执行结果总结

针对标准运维单次任务的执行结果进行标准化总结。用户提供 `bk_biz_id` 与 `task_id` 后，通过任务总结工具拉取任务上下文数据，Skill 据此输出：整体概览、成功节点耗时排名、失败节点卡片、潜在风险分析与总结建议。

## 概述

本 Skill 对标准运维单次任务的执行结果进行标准化总结。用户提供 `bk_biz_id` 与 `task_id` 后，通过任务总结工具拉取任务上下文数据，Skill 据此输出：整体概览、成功节点耗时排名、失败节点卡片、潜在风险分析与整体总结。

| 能力 | 说明 |
|------|------|
| **整体概览** | 展示所属业务、任务名称、业务 ID、任务 ID、任务状态、总耗时、有效执行时间、成功/失败节点数 |
| **耗时排名** | 按耗时对成功节点排序，帮助识别性能瓶颈 |
| **失败节点卡片** | 区分普通节点与子流程节点，完整展示失败信息与原因分析 |
| **潜在风险分析** | 识别有重试记录（`retry > 0`）的节点，提示潜在稳定性风险 |
| **分析总结** | 整体情况评估、主要问题原因、改进建议 |

**解决痛点**：
- 用户拿到任务原始数据，难以快速掌握执行全貌
- 失败节点信息分散在 `ex_data` / `failed_children_execution_info` 中，层级复杂
- 曾经重试成功的节点隐藏了稳定性风险，容易被忽略

## 上下文需求清单

| 步骤 | 所需上下文 | 来源 | 必需/可选 | 缺失时处理 |
|------|-----------|------|----------|-----------|
| 信息收集 | `bk_biz_id` 与 `task_id` | 用户输入 / handoff(`task-monitor`、`bk-sops-troubleshooter`) | 必需 | 询问用户 |
| 信息收集 | 任务执行结果（含成功节点、失败节点、耗时、重试次数） | API: `get_task_detail` + `get_task_node_detail` / handoff 已收集数据 | 必需 | 调用 API |
| 失败节点分类 | `failed_children_execution_info` 是否为空 | 返回数据 | 必需 | 视为普通节点 |
| 风险识别 | 各成功节点的 `retry` 字段 | 返回数据 | 必需 | 视为无重试 |

## 工作流程

### Step 1：问题收集

根据用户输入类型，采用不同方式收集问题信息：

| 输入类型 | 处理方式 |
|----------|----------|
| **用户提供 `bk_biz_id` + `task_id`** | 直接调用任务总结工具获取任务上下文 |
| **仅提供 `task_id`，未提供业务** | 引导用户补充 `bk_biz_id`；若可从对话上下文推断，需向用户确认 |
| **未提供任何 ID** | 引导用户提供，或询问是否需要通过任务列表工具查找目标任务 |
| **从 handoff 转入** | 接收上下文包（含 `bk_biz_id`、`task_id`），直接使用已有数据 |

**输出**：确认要总结的任务标识（业务 ID + 任务 ID）。

---

### Step 2：节点分类识别

对返回数据中的节点按类别处理，决定后续展示模板：

| 节点类别 | 判定依据 | 处理方式 |
|---------|---------|---------|
| **成功节点** | 位于「执行成功节点信息列表」 | 参与耗时排名；若 `retry > 0` 则纳入潜在风险分析 |
| **普通失败节点** | 位于失败列表且 `failed_children_execution_info` 为空 | 使用普通失败卡片模板 |
| **子流程失败节点** | 位于失败列表且 `failed_children_execution_info` 非空 | 使用子流程失败卡片模板，用 `└─` 缩进展示内部失败子节点 |

---

### Step 3：内容分析与生成

#### 3.1 整体概览

从返回数据提取以下字段并按「整体概览」模板输出：`project_name`（所属业务）、`task_name`（任务名称）、`bk_biz_id`（业务 ID）、`task_id`（任务 ID）、任务状态、任务执行耗时、任务有效执行时间、执行成功节点数、执行失败节点数。

> **有效执行时间兜底**：当任务暂未执行完成或执行失败时，显示「任务暂未执行完成，无法获取任务有效执行时间」。

#### 3.2 耗时排名

- 从执行成功节点信息列表提取 `node_name` 与耗时；
- 按耗时降序排列，输出表格；
- **表格中的节点名称严格按 `node_name` 输出，禁止自行生成或截断**。

#### 3.3 失败节点卡片

对每个失败节点，选择对应模板生成卡片：

**普通节点失败**（`failed_children_execution_info` 为空）：
- 完整展示 `ex_data` 中的失败信息，**不截断、不省略**；
- 结合失败信息中的问题给出「原因分析」。

**子流程节点失败**（`failed_children_execution_info` 非空）：
- 子流程本身显示「因内部节点执行失败」；
- 用 `└─` 缩进展示内部失败的子节点，逐个给出子节点的失败信息与原因分析。

> **原因分析必备要素**（写入卡片「原因分析」字段时**必须体现**）：
> 1. **失败根因**（如通知对象未配置、目标主机连接失败、脚本报错等）；
> 2. **可能的原因**（结合失败信息与业务背景推断）；
> 3. **排查方向**（明确用户应该检查哪个配置项/节点/环境）。

#### 3.4 潜在风险分析

- 遍历执行成功节点信息列表，识别 `retry > 0` 的节点；
- 每个此类节点视为一个潜在风险；
- 结合插件名称分析可能的失败原因；
- 表格中的节点名称从成功节点列表中获取。

**常见潜在风险类别**：

| 风险类型 | 特征 | 典型场景 |
|---------|------|---------|
| **稳定性风险** | 节点重试后才成功 | 网络抖动、下游服务不稳定、agent 偶发异常 |
| **性能风险** | 节点耗时占比过高 | 备份/传输节点耗时长、串行执行阻塞后续节点 |
| **业务风险** | 涉及重启/发布等敏感操作 | 服务重启可能导致短暂中断 |

#### 3.5 分析总结

结合以上信息给出整体总结，包括：
- 任务执行整体情况评估（成功率、耗时占比）；
- 主要问题及原因分析；
- 改进建议（针对失败节点与潜在风险）。

---

### Step 4：输出规范

#### 4.1 空数据兜底

| 场景 | 兜底文案 |
|------|---------|
| 失败节点列表为空 | 「没有执行失败的节点」 |
| 潜在风险分析无节点 | 「没有潜在风险」 |
| 有效执行时间无法获取 | 「任务暂未执行完成，无法获取任务有效执行时间」 |

> **禁止输出空表格**：当分类无节点时，必须以说明文案代替表格。

#### 4.2 输出禁止事项

- **禁止在正文使用原始 JSON 字段名**（如 `failed_children_execution_info`、`ex_data`、`retry`、`node_name` 等），必须用自然语言描述；
- **禁止自行生成或截断节点名称**，表格中的节点名称严格按返回数据的 `node_name` 输出；
- **禁止截断或省略失败信息**，`ex_data` 内容必须完整展示，方便用户查看原始错误；
- **禁止跨任务/跨业务信息泄露**，仅输出当前任务的总结结论；
- **敏感值脱敏**：失败信息中出现的密码、AK/SK、Token、私钥等，输出时脱敏为 `pass****`。

#### 4.3 卡片式列表格式

- 整个卡片（含标题和内容）都用 Markdown 引用块 `>` 包裹，实现整体缩进；
- 每个字段之间用空引用行（单独一行 `>`）分隔，确保换行显示；
- 子流程节点使用两层引用（`> > `）表示内部子节点，配合 `└─` 缩进符号。

#### 4.4 输出格式

请不要输出寒暄语，直接按以下 Markdown 结构输出。**所有小节标题必须以 `### ` 开头**（包括第一个标题）：

**① 任务执行情况的整体概览**

```markdown
### 任务执行情况的整体概览

- **所属业务**: **[所属业务名称]**
- **任务名称**: **[任务名称]**
- **业务ID**: **[业务ID]**
- **任务ID**: **[任务ID]**
- **任务状态**: **[成功/失败]**
- **任务执行耗时**: **[任务执行耗时]**
- **任务有效执行时间**: **[任务实际在执行的时间，不包含人工等待时间；未完成或失败时显示兜底文案]**
- **执行成功节点数**: **[执行成功的节点数]**
- **执行失败节点数**: **[执行失败的节点数]**
```

**② 执行成功节点的耗时排名**

```markdown
### 执行成功节点的耗时排名

| 节点名称 | 耗时 |
|----------|------|
| [节点名称] | [耗时] |
```

**③ 失败节点信息**

以卡片式列表展示每个失败节点。**整个卡片（含标题和内容）都用引用块 `>` 包裹**，字段之间用空引用行分隔。

- 普通节点失败卡片：

```markdown
> #### [普通节点名称]
> **失败信息**: [完整的失败信息]
>
> **原因分析**: [根据失败信息分析可能的原因]
```

- 子流程节点失败卡片（用 `└─` 缩进展示内部失败子节点）：

```markdown
> #### [子流程节点名称]（因内部节点执行失败）
> **└─ [子节点名称]**
> > **失败信息**: [完整的失败信息]
> >
> > **原因分析**: [根据失败信息分析可能的原因]
```

- 无失败节点时：

```markdown
### 失败节点信息

没有执行失败的节点。
```

**④ 潜在风险分析**

```markdown
### 潜在风险分析

| 节点名称 | 潜在风险 |
|----------|----------|
| [节点名称] | [潜在风险] |
```

- 无潜在风险时：

```markdown
### 潜在风险分析

没有潜在风险。
```

**⑤ 分析总结**

```markdown
### 分析总结

[整体情况评估 + 主要问题及原因分析 + 改进建议]
```

## 输出示例

### 任务执行情况的整体概览

- **所属业务**: **蓝鲸运维平台**
- **任务名称**: **服务器日常巡检**
- **业务ID**: **555**
- **任务ID**: **12345**
- **任务状态**: **失败**
- **任务执行耗时**: **5分30秒**
- **任务有效执行时间**: **4分20秒**
- **执行成功节点数**: **8**
- **执行失败节点数**: **2**

### 执行成功节点的耗时排名

| 节点名称 | 耗时 |
|----------|------|
| 数据备份 | 2分15秒 |
| 文件传输 | 1分30秒 |
| 配置更新 | 45秒 |

### 失败节点信息

> #### 消息通知
> **失败信息**: 参数校验未通过，未选择通知对象
>
> **原因分析**: 节点配置中未指定通知对象，建议检查通知节点的收件人配置

> #### 服务器部署子流程（因内部节点执行失败）
> **└─ 部署**
> > **失败信息**: 任务执行失败，前往作业平台(JOB)查看详情
> >
> > **原因分析**: JOB 任务执行异常，可能是目标主机连接失败或脚本执行出错，建议前往 JOB 平台查看详细日志

### 潜在风险分析

| 节点名称 | 潜在风险 |
|----------|----------|
| 数据备份 | 执行耗时较长，可能存在性能瓶颈 |
| 服务重启 | 重启操作可能导致短暂服务中断 |

### 分析总结

本次任务整体执行情况良好，共 8 个节点执行成功，2 个节点执行失败。任务有效执行时间为 4 分 20 秒，占总耗时的 78.8%。失败节点主要集中在通知和脚本执行环节，建议检查通知配置和主机权限设置。数据备份节点耗时较长，建议后续优化备份策略或增加并行度以提升执行效率。

## 关键 API

| API | 用途 | MCP Server |
|-----|------|------------|
| `get_task_detail` | 获取任务详情（含节点列表、执行状态、耗时） | `bk-sops-prod-task` |
| `get_task_node_detail` | 查询任务节点执行详情（含重试次数 `retry`） | `bk-sops-prod-task` |
| `get_task_node_log` | 获取节点执行日志（辅助原因分析） | `bk-sops-prod-task` |
| `get_template_info` | 获取流程模板信息（节点插件类型等） | `bk-sops-prod-template` |

> 接入 MCP Server：`bk-sops-prod-task`（任务管理）+ `bk-sops-prod-template`（流程模板）

## 操作确认

本 Skill 默认为**只读总结**，不涉及写操作。如总结结论建议用户执行重试、跳过、修改参数重跑等操作，请按 handoff-protocol 转交 `bk-sops-troubleshooter` 或 `bk-sops-task-runner` 执行。

---

## 操作验证

本 Skill 不执行写操作，无需操作验证。如后续用户依据总结建议进行修复，可再次触发本 Skill 对新任务实例进行总结。

## 与其他 Skill 的衔接

| 方向 | 来源/目标 | 分级 | 衔接方式 |
|------|----------|------|---------|
| 入 | **task-monitor → 本 Skill** | 建议 | 快速监控发现任务执行完成后，可转入本 Skill 输出标准化总结报告 |
| 入 | **bk-sops-troubleshooter → 本 Skill** | 建议 | 深度排查后，可用本 Skill 生成给用户看的最终总结报告 |
| 出 | **本 Skill → bk-sops-abalyze-task-error** | 建议 | 总结中存在失败节点、用户希望深入定位根因时，转交由其输出失败原因分析报告 |
| 出 | **本 Skill → bk-sops-troubleshooter** | 建议 | 总结中出现多个潜在风险、需要跨节点/跨任务排查时，向用户推荐 |
| 出 | **本 Skill → bk-sops-task-runner** | 建议 | 需要对失败节点执行重试/跳过/修改参数重跑操作时，转交由其完成确认与执行 |
