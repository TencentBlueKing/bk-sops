## 游戏类型如何影响流程设计

### 1. 服务器架构差异决定流程结构
- **FPS/MOBA/BR**：大多采用 Match-Based 架构（匹配制），发布时需关注 CLB 流量摘除、进程灰度重启
- **经典 MMORPG**：采用分区分服架构，流程围绕区服管理（合服/开服/开区）展开，流程最复杂
- **动作格斗 RPG**：兼有分区分服和 Match 特征，客户端版本管理（做包/资源上传）是独特需求
- **SLG 策略 RPG**：分区分服为主但偏轻量化，区服运营状态管理（维护/白名单/开关服）是核心
- **开放世界生存**：新一代架构，GCloud + BCS 双轨部署，BKChat 驱动运维协作
- **自走棋/策略对战**：容器化程度最高（BCS/Helm），大量并行节点部署
- **休闲棋牌**：单节点流程为主，蓝盾流水线驱动自动化
- **竞速类**：TCM 配置中心 + 分批灰度发布，CLB 权重管理精细
- **音舞类**：配置/CDN 更新为主，DB SQL 变更频繁
- **派对竞技**：DS 架构 + PAK 更新 + 七彩石配置管理，AI 运维最先进
- **沙盒创造**：Helm + GCloud 双轨、安全补丁管理、条件并行分支最复杂

### 2. 更新频率影响流程复杂度
- **MOBA/FPS**：版本更新频繁但单次变更相对原子化，热更/不停服更新占比高
- **经典 MMORPG**：停服更新是主流模式，单次发布流程节点数多（p75=9，max=174）
- **自走棋策略对战**：BCS 部署标准化，但多区域并行部署节点数最多（p75=9，max=87）
- **休闲棋牌**：更新简单（中位=1），蓝盾流水线处理大部分逻辑

### 3. 核心组件使用差异

| 组件 | 最强依赖类型 | 说明 |
|------|-------------|------|
| tcm_execute_task | BR > 动作格斗 > 竞速 | TCM 密度与实时性要求正相关 |
| gcs_bill_execute | 经典 MMORPG > SLG 策略 > 音舞 | 分区分服的 GCS 工单体系 |
| clb_modify_weight | BR > 竞速 > 自走棋 | CLB 权重管理需求 |
| gcloud_pre_publish | 经典 MMORPG > 开放世界 > 沙盒 | GCloud 发布体系 |
| bk_http_request | 休闲棋牌 | 蓝盾流水线 API 驱动 |
| devops-pl-plugin | 休闲棋牌 > 动作格斗 | 蓝盾流水线集成 |
| bkchat-sops-send | 开放世界 > 音舞 > 经典 MMORPG | BKChat 协作密度 |
