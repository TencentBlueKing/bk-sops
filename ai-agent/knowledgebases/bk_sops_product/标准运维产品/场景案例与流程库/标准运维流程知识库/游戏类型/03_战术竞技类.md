> 战术竞技类游戏以大地图多人生存对战为核心，服务器架构强调大规模并发和动态资源管理。运维流程特点是平均节点数全类型最高（9.6）、CLB 权重管理为独特核心需求、TCM 配置管理密度最高。

## 关键检查点（Review 要点）

1. **CLB 权重变更闭环**：这是 BR 类流程的核心模式。必须检查：摘流量（权重→0）→ 操作 → 恢复流量（权重→100）的完整闭环
2. **四层权重管理一致性**：hcm-weight-four 使用 368 次，需确认所有 RS 的权重变更是否一致
3. **TCM 配置变更原子性**：TCM 密度 2.45 次/流程，单个流程中多次 TCM 操作需要确保顺序正确、回滚可控
4. **人工确认节点位置**：pause_node 密度 1.56 次/流程全类型最高，需验证确认节点是否在关键操作前后
5. **PAK 文件分发校验**：部分业务有专门的 PAK 文件分发检查流程，需确保 MD5 校验完整
6. **扩缩容流程完整性**：扩容（4.4%）和缩容（3.9%）占比较高，需检查 bus 配置刷新、进程启动、健康检查的完整链路
7. **BKAI Agent 集成**：AI 相关流程占 3.9%，需检查 AI Agent 调用的超时和异常处理

## 代表性流程

**流程 1**：PAK 文件分发检查（8 节点）
```
开始 → 获取待检查IP列表 → 生成待检查内容文件 → 分发待检查文件到DS → 快速执行脚本 → 任务日志初处理 → 对比检查 → 统计机器数 → 生成检查报告 → 结束
```
> 特点：PAK 文件完整性校验的标准模式

**流程 2**：分组 lobby 一键扩容（19 节点）
```
开始 → 确认TCM配置 → 同步目录 → 等待2分钟 → 启动lobby进程 → 检查通道加载日志 → 检查配置 → 检查版本号 → 生成配置并下发 → 刷新bus → 配置gslb → 暂停 → 确认同步 → checkconf → 结束
```
> 特点：扩容流程涉及 TCM + bus 刷新 + GSLB 配置的完整链路

**流程 3**：下发 perf 录制请求（17 节点）
```
开始 → 定时 → perf录制开始 → 下发请求 → 定时 → perf录制结束 → 解压tgz → perfdata转json → 生成火焰图推送群组 → profiling推送群聊 → AI分析ue-profiling → 结束
```
> 特点：性能分析 + AI 辅助的高级运维流程
