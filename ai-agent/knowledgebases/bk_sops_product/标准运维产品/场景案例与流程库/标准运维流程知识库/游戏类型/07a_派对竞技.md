> 派对竞技类游戏采用 DS（Dedicated Server）架构，以 UGC 派对玩法为核心。运维流程特点是 **AI 运维使用最密集（23.6%）**、排他网关率极高（22.8%）、PAK 文件更新+七彩石配置管理是独特模式、DS 架构的 DSA/DSC reload+同步检查是核心操作。
>
> **347** 条流程 | **5** 个业务 | 平均节点数 4.5 | 中位节点数 3

## 关键检查点（Review 要点）

1. **PAK 文件一致性**：PAK 更新是核心流程。标准链路：`加Lock → PAK解压 → 判断类型(starp-pak?) → 七彩石追加/提交 → DSA reload → 检查DSA同步 → DSC reload → 检查DSC同步 → 解Lock → 通知`
2. **Lock 文件管理闭环**：PAK/DSA 更新使用 lock 文件防止并发，必须确保加锁→操作→解锁的完整闭环，异常分支也需解锁
3. **DSA/DSC 同步状态验证**：每次 reload 后必须有同步状态检查，确认配置已生效
4. **七彩石配置原子性**：PAK 版本号通过七彩石管理，需确保配置更新和提交的原子性
5. **AI Core 分析完整性**：AI 分析 Corefile 流程（解析告警→GDB判断→堆栈解析→分析→邮件），需确认异常分支处理
6. **条件分支覆盖**：排他率 22.8%，每个排他分支都需有对应处理（如 starp-pak / 非 starp-pak）

## 代表性流程

**流程 1**：PAK 更新（12 节点）
```
人工确认 → 添加lock → pak解压 → [排他] 是否starp-pak → [是] 七彩石追加版本号 / [否] 七彩石提交更新 → dsa reload → 检查dsa同步 → dsc reload → 检查dsc同步 → 删除lock → 发送消息
```
> 特点：PAK 更新的标准模式 — lock 保护 + 条件分支 + DS reload + 同步检查

**流程 2**：AI 分析 Corefile（9 节点）
```
解析Core告警 → [排他] 是否GDB进程 → [是] 提取服务名+ds包 → 传BIN到运维机 → 传Core到运维机 → GDB堆栈解析 → 解压BIN → 堆栈分析 → 发送邮件
```
> 特点：AI 自动分析 Core dump 的智能运维流程

**流程 3**：DSA 更新（11 节点）
```
人工确认 → 添加lock → 检查sp-pak → 七彩石配置更新 → 七彩石配置提交 → dsa reload → 检查dsa同步 → dsc reload → 检查dsc同步 → 删除lock → 发送消息
```
> 特点：与 PAK 更新类似的 lock+reload+check 模式
