# MOBA 类

> MOBA 类游戏以 5v5 或多人实时对战为核心，服务器架构通常为匹配服+游戏服分离模式。运维流程特点是灰度发布极为精细（按进程/按区域逐步推进）、配置热更频繁、与蓝盾 CI/CD 深度联动。
>
> **1,379** 条流程 | **14** 个业务 | 平均节点数 6.0 | 中位节点数 3

## 关键检查点（Review 要点）

1. **灰度发布策略粒度**：MOBA 灰度发布是按进程级别推进的（如"灰度 reload 第一个进程 → 确认 → 全量"），Review 时需检查灰度范围是否合理
2. **配置变更回滚能力**：配置相关流程占比 8.4%，需检查配置变更前是否有备份/diff、变更后是否有验证
3. **进程 reload 安全性**：reload 操作频繁，需确保 reload 前有流量摘除或灰度策略
4. **RPC 调用容错**：power-plugin-rpc 在 MOBA 类游戏中重度使用，需检查 RPC 调用的超时和重试配置
5. **多区域一致性**：安卓/iOS 双平台 + QQ/微信双渠道，配置推送需确保所有渠道覆盖
6. **蓝盾流水线状态同步**：devops-pl-plugin 使用频繁，需检查 CI/CD 流水线状态与 SoPS 流程的联动
7. **审批流程完整性**：bk_approve 使用率高，核心变更必须有审批节点

## 代表性流程

**流程 1**：限频文件刷新（10 节点）
```
开始 → 生成配置差异 → 审批 → 灰度分发 → 检查文件md5 → 通知检查 → 全量分发 → 通知检查 → 备份文件 → 上传文件到中转服务器 → 结束
```
> 特点：灰度→全量的标准分发模式，有 MD5 校验

**流程 2**：服务器进程配置修改（15 节点）
```
开始 → 确认灰度情况 → 提取灰度IP → 生成配置差异 → 确认配置差异 → 灰度机器配置修改 → 灰度reload第一个进程 → 通知检查 → 确认 → 全量配置修改 → 通知检查 → 通知完成 → 结束
```
> 特点：进程级灰度 reload + 配置差异确认

**流程 3**：停服更新（22 节点）
```
开始 → 蓝鲸监控告警屏蔽 → gcloud区服置灰 → 下载BuildInfo → 解析BuildInfo → 停服子流程 → 删除旧应用 → 部署声明上传Git → 创建新应用 → PowerApp同步更新 → 区服点亮 → 检查 → 结束
```
> 特点：K8S 容器化部署 + PowerApp + GCloud 区服管理的新一代模式
